# Grundsatzentscheidungen (ADR-000 … ADR-010)

Dieses Dokument enthält die mit dem Auftraggeber abgestimmten Grundsatzentscheidungen. Sie sind **bindend** für alle weiteren Architektur-Dokumente und für jeden Implementierungs-Agenten. Weicht ein Dokument davon ab, gilt dieses Dokument.

## Konsequenzen

- **ADR-001:** Das Entitlement-/Lizenz-Subsystem des Originals (Monitor/Prime, `Instance.edition`, Plan-Matrix, Upgrade-Komponenten in `apps/web/components/license`, `apps/web/components/workspace/billing`, `packages/constants/src/subscription.ts`, `payment.ts`) wird **nicht** portiert. Limits der Pläne (z. B. „5.000 Automationen“, „Page-Versionen 2 Tage“) entfallen bzw. werden zu frei konfigurierbaren Instanz-Einstellungen mit großzügigen Defaults.
- **ADR-002:** Kein Node.js zur Laufzeit. Der PDF-Export des Live-Servers (heute `@react-pdf/renderer`) wird ebenfalls in .NET umgesetzt.
- **ADR-003:** Es entfällt die Pflicht zur Tabellen-/Spaltenkompatibilität. Trotzdem werden die **JSON-API-Verträge fachlich am Original orientiert** (Ressourcen, Feldnamen in `snake_case`, Enum-Werte, Fehlercodes), weil das Angular-Frontend die Store-/Service-Logik des Originals 1:1 portiert. Das senkt Übersetzungsfehler und erlaubt Contract-Tests gegen das Original.
- **ADR-007 – Umfang der Forgejo-Integration** (Mindestumfang; orientiert am Funktionsumfang der GitHub-/GitLab-Integrationen der Commercial Edition, siehe `migration/features/28-paid-integrationen-importer-ai.md`, darüber hinaus erweiterbar):
  - **Verbindung:** eine oder mehrere Forgejo-Instanzen pro Workspace (selbst gehostet, auch im Airgapped-Netz), OAuth2-Anwendung auf Forgejo-Seite, Organisationen/Repositories auswählen; zusätzlich persönliche Konto-Verknüpfung je Nutzer, damit Aktionen dem richtigen Nutzer zugeordnet werden.
  - **Repository ↔ Projekt-Mapping** mit konfigurierbarer Zuordnung von States, Labels, Prioritäten und Nutzern.
  - **Issue-Sync** bidirektional oder einseitig wählbar: Titel, Beschreibung, State, Labels, Assignees, Kommentare, Sub-Issues/Abhängigkeiten soweit Forgejo sie abbildet; Konfliktregeln und Wiederaufnahme nach Ausfällen.
  - **Pull-Request-Automation:** Referenzen auf Work Items in Branch-Namen, PR-Titeln, -Beschreibungen und Commits (z. B. `PROJ-123`, „Fixes PROJ-123“) verknüpfen PRs/Commits automatisch; PR-Zustände (Draft, Open, Review requested, Merged, Closed) lösen konfigurierbare State-Wechsel aus.
  - **Sichtbarkeit in Plane:** verknüpfte Branches, Commits, PRs und deren Status (inkl. Forgejo-Actions-Checks) im Work Item und in dessen Activity; Link-Previews für Forgejo-URLs.
  - **Aus Plane heraus:** Branch-Namen aus einem Work Item erzeugen bzw. kopieren, PR zu einem Work Item öffnen.
  - **Webhooks** von Forgejo mit Signaturprüfung (HMAC-SHA256), idempotente Verarbeitung über das Event-/Outbox-System.
  - **Importer:** Forgejo-Issues, Labels und Milestones eines Repositories einmalig in ein Plane-Projekt übernehmen.
  - **Login:** kein eigener Forgejo-Login in Plane. Plane und Forgejo hängen beide an Keycloak (ADR-008), dadurch gibt es Single Sign-on und eine eindeutige Zuordnung der Nutzer zwischen beiden Systemen (gleiche Keycloak-Identität). Die persönliche Konto-Verknüpfung für API-Aktionen im Namen des Nutzers bleibt über die OAuth2-App auf Forgejo-Seite.
  - **Technik:** Forgejo-REST-API (Gitea-kompatibel, `/api/v1`), eigener typisierter .NET-Client; Integrationstests gegen einen echten Forgejo-Container in Aspire. Forgejo ist ab v9 unter GPL-3.0-or-later lizenziert und läuft als eigenständiger Dienst (kein Code-Linking), kann eine eigene Datenbank auf dem gemeinsamen PostgreSQL-Server nutzen.
- **ADR-008 – Anmeldung über Keycloak (OIDC):**
  - **Ablauf:** Klick auf „Anmelden“ bzw. Aufruf einer geschützten Route → Weiterleitung zu Keycloak (Authorization Code + PKCE) → Rückkehr zur Plane-API, die eine serverseitige Session anlegt (HttpOnly-Cookie wie im Original, kein Token im Browser-Speicher; Backend-for-Frontend-Muster). Abmeldung über RP-initiated Logout, zusätzlich Back-Channel-Logout von Keycloak, damit Sessions bei Sperrung oder Abmeldung in Keycloak sofort enden.
  - **Benutzeranlage:** Just-in-time beim ersten Login aus den Claims (`sub` als feste Verknüpfung, `email`, `email_verified`, Name, Avatar). Ausstehende Workspace-/Projekt-Einladungen werden über die E-Mail-Adresse zugeordnet (CE-AUTH-028 bleibt). Nur Konten mit verifizierter E-Mail werden angelegt.
  - **Rollen:** Instanz-Admin (God Mode) ergibt sich aus einer Keycloak-Rolle bzw. Gruppe (konfigurierbar, z. B. `plane-instance-admin`), nicht mehr aus einem eigenen Admin-Login. Workspace- und Projektrollen werden weiterhin in Plane verwaltet; eine automatische Zuordnung aus Keycloak-Gruppen ist das Paket E3 (IdP Group Sync).
  - **Space (öffentliche Boards):** Lesen bleibt anonym; Kommentieren, Reagieren und Abstimmen erfordern eine Keycloak-Anmeldung.
  - **Maschinenzugriff:** API-Keys (`X-API-Key`) für die Public API bleiben, da sie kein Login sind. Ob Tokens für spätere Plane-Apps/MCP (Paket H1) ebenfalls Keycloak ausstellt, wird im Architektur-Rahmen entschieden (Empfehlung: ja, Keycloak als Autorisierungsserver statt eigenem OAuth2-Server).
  - **Wegfall in der CE-Portierung:** CE-AUTH-002 bis -011, -013, -017 bis -021 (Registrierung, Passwort, Magic-Code, OAuth-Provider, Steuerung der Auth-Methoden), CE-INST-007 und CE-INST-020 bis -024 (Admin-Login, Provider-Konfiguration im God Mode), CE-SPACE-008 bis -011 (Space-Login-Varianten), CE-PROF-007 (verknüpfte OAuth-Konten). **Angepasst:** CE-AUTH-001 (Sign-in-Seite wird Einstieg mit „Mit Keycloak anmelden“ bzw. direkte Weiterleitung), CE-AUTH-012, -014, -022 bis -027, -029, -030, CE-INST-004 (Instanz-Admins: Spiegel der Keycloak-Rolle, Pflege in Keycloak), CE-INST-006 (Erst-Einrichtung ohne Admin-Konto), CE-PROF-005 (Konto deaktivieren wirkt in Plane; Sperre des Kontos selbst in Keycloak).
  - **Bezahl-Pakete:** E1 (SAML/OIDC-SSO), E2 (Workspace-Identity/Domains), E4 (2FA, Passkeys, Password Policy) und LDAP aus E3 werden **nicht in Plane gebaut**, sondern durch Keycloak abgedeckt (Identity Brokering für SAML/OIDC, User Federation für LDAP/AD, OTP und WebAuthn/Passkeys, Passwort-Richtlinien, Domain-Regeln). E3 behält IdP Group Sync (Keycloak-Gruppen → Plane-Rollen) und optional SCIM.
  - **1:1-UI:** Die Anmeldeseite liegt jetzt in Keycloak. Damit die Optik dem Original entspricht, bekommt Keycloak ein eigenes Login-Theme im Plane-Design (Layout, Farben, Schriften der Original-Sign-in-Seite aus `apps/web` bzw. `apps/space`).
  - **Technik:** Keycloak (Apache-2.0) als Aspire-Ressource mit Realm-Import (Clients für web/admin/space, Forgejo als weiterer Client, Testbenutzer für Dev/Test); ASP.NET Core OpenID-Connect-Handler; Integrationstests gegen einen echten Keycloak-Container.
- **ADR-010 – Branding:**
  - **Visuelle Parität:** Screenshot-Vergleiche gegen das Original maskieren Markenelemente (Logo, Produktname) bzw. vergleichen gegen Referenzen, in denen das Original-Branding vorab ersetzt wurde; jede Ersetzung steht in der Abweichungsliste als `BRAND-*`.
  - **Texte:** „Plane“ in Strings wird durch „funk.“ ersetzt, auch in zusammengesetzten Begriffen („Plane AI“ entfällt mangels Paket G; „Plane-Apps“ → „funk.-Apps“). Begriffe aus dem Original-Fachvokabular (Work Items, Cycles, Modules, Pages, Intake) bleiben.
  - **Externe Links** auf plane.so, docs.plane.so, GitHub/Forum von Plane entfallen oder zeigen auf konfigurierbare eigene Ziele (ADR-004).
  - **Rechtliches:** „Plane“ ist eine Marke der Plane Software, Inc.; sie wird in der Oberfläche nicht verwendet. Der AGPL-Herkunftshinweis auf das Original (Copyright/Lizenz) bleibt in LICENSE/NOTICE und im About-Dialog erhalten.
- **ADR-004:** Alle Assets (Fonts, Icons, Emoji-Daten, Editor-Plugins) werden gebündelt ausgeliefert. Container-Images müssen ohne Internetzugang startbar sein.
